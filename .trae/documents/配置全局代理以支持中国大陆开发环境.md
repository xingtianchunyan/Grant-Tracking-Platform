# 配置本地代理环境以解决网络问题

用户明确指出开发环境位于中国大陆，且已设置本地代理端口为 `7078`。虽然 `.env` 配置已完成，但 Node.js 应用程序（特别是 `discord.js` 和 `node-fetch`）默认不会自动读取系统的代理设置或 `.env` 中的代理变量，除非明确配置。

## 目标
确保 `discord-commander.ts` 和其他后端脚本在运行时能够通过本地代理（`http://127.0.0.1:7078`）访问外部 API（Discord, GitHub, SiliconFlow）。

## 实施方案

### 1. 引入 `undici` 或 `https-proxy-agent`
由于 `discord.js` 使用 `undici` (在 Node 18+) 或其他底层请求库，我们需要一种全局的方式来应用代理。在 Node.js 中，最简单的方法通常是使用 `undici` 的 `ProxyAgent` 或全局设置 `dispatcher`。

然而，更通用的做法是在应用入口处（如 `discord-commander.ts` 的顶部）检测代理环境变量，并配置全局的 HTTP/HTTPS Agent。

### 2. 修改 `discord-commander.ts`
我们将添加一段代码，在 `Client` 初始化之前，检查 `HTTP_PROXY` 或 `HTTPS_PROXY` 环境变量。如果存在，则配置全局代理。

*   **注意**：`discord.js` v14+ 允许通过 `REST` 选项传递 `agent`。
*   或者，更简单的做法是利用 `undici` 的全局 dispatcher 设置（Node.js v18.x+ 原生 fetch 也是基于 undici 的）。

### 3. 配置步骤
1.  **安装 `undici`** (如果尚未安装，虽然 Node 自带，但显式安装可以获得 `ProxyAgent`)。查看 `package.json`，发现项目使用了 `node-fetch`。
    *   `node-fetch` 需要 `https-proxy-agent`。
    *   `discord.js` 内部机制可能不同。

为了确保兼容性，我们将采取以下策略：
*   **Discord.js**: 它会自动尊重 `HTTPS_PROXY` 吗？不一定。我们需要显式设置。
*   **Fetch**: `node-fetch` 需要手动传递 agent。

**更稳健的方案**: 使用 `global-agent` 或在代码中手动修补。但最简单且侵入性最小的方法是设置 `undici` 的全局 Dispatcher，因为 `discord.js` 新版本和 Node 20+ 的 fetch 都倾向于使用它。

**计划**：
1.  在 `scripts/discord-commander.ts` 顶部添加代理配置逻辑。
2.  使用 `undici` 的 `ProxyAgent` 来设置全局代理（如果检测到环境变量）。
3.  由于用户说已经配置了环境变量，我们假设运行环境中有 `HTTPS_PROXY`。如果没有，我们可以在代码里硬编码读取 `.env`。

### 4. 具体代码修改
我们将修改 `scripts/discord-commander.ts`。

```typescript
import { ProxyAgent, setGlobalDispatcher } from "undici";

if (process.env.HTTPS_PROXY) {
  const proxyAgent = new ProxyAgent(process.env.HTTPS_PROXY);
  setGlobalDispatcher(proxyAgent);
  console.log(`[PROXY] Enabled proxy: ${process.env.HTTPS_PROXY}`);
}
```

**依赖检查**：需要确认是否需要安装 `undici` 包。`package.json` 中没有显式列出 `undici`，但 `discord.js` 依赖它。为了安全起见，我们可以直接使用 `node-fetch` 的代理配置方式，或者尝试设置 `undici`。

鉴于 `package.json` 只有 `node-fetch`，且 `discord.js` 版本是 `latest`（可能是 v14）。`discord.js` v14 依赖 `undici`。

**备选方案**：如果在 `package.json` 中没有 `undici`，我们直接使用 `https-proxy-agent` 配合 `node-fetch` 可能会比较麻烦（需要修改所有 fetch 调用）。
最优雅的方式是：**设置 Node.js 的全局代理行为**。

用户提到“请确保所有外部API请求...都通过本地代理”。
我们将安装 `undici`（如果是 Node 18+ 环境，这通常是处理 fetch 代理的最佳实践）。

### 5. 验证
修改后，重启服务，观察日志是否显示代理已启用，以及 Discord 连接是否成功。

**超时设置**：用户提到“网络超时设置已适当调整”。我们可以在 `discord-commander.ts` 的重试逻辑中增加超时时间（目前是 5s 重试间隔，fetch 默认超时较长）。

## 执行步骤
1.  **检查环境**：确认 `HTTPS_PROXY` 是否在 `config.ts` 中被加载（虽然 config 没导出它，但 `process.env` 会有）。
2.  **安装 `undici`**：`npm install undici`。
3.  **修改 `discord-commander.ts`**：引入 `undici` 并配置全局 Dispatcher。
4.  **修改 `risk-scan.ts`**：同样的，为了让 GitHub API 请求也走代理，也需要在那里应用同样的逻辑（或者提取一个公共的 `setup-proxy.ts`）。

为了简化，我们将创建一个 `lib/proxy.ts` 文件，并在所有入口脚本 (`discord-commander.ts`, `risk-scan.ts`, `scheduler.ts`) 顶部引入它。

**文件名**: `lib/proxy.ts`
**内容**:
```typescript
import { ProxyAgent, setGlobalDispatcher } from "undici";

const proxyUrl = process.env.HTTPS_PROXY || process.env.HTTP_PROXY;

if (proxyUrl) {
  try {
    const dispatcher = new ProxyAgent(proxyUrl);
    setGlobalDispatcher(dispatcher);
    console.log(`[PROXY] Global proxy agent configured for: ${proxyUrl}`);
  } catch (err) {
    console.error("[PROXY] Failed to configure global proxy:", err);
  }
}
```

这样可以一劳永逸地解决 `fetch` 和 `discord.js` 的代理问题（假设它们都使用 `undici` 或原生 `fetch`）。对于 `node-fetch`，它**不使用** `undici` 的全局 dispatcher。我们需要确认项目中的 `fetch` 是来自 `node-fetch` 还是原生 `fetch`。
`scripts/discord-commander.ts` 第一行：`import fetch from "node-fetch";`
这说明它用的是 `node-fetch`。`node-fetch` **不会** 自动走系统代理，也不理会 `undici` 设置。

**修正计划**：
1.  将 `scripts/discord-commander.ts` 中的 `import fetch from "node-fetch"` 移除，改用 Node.js 原生 `fetch` (Node 18+ 支持)。
2.  或者，保留 `node-fetch` 但必须使用 `https-proxy-agent`。
3.  考虑到 Node.js 版本要求 `>= 20`（README 中提到），我们可以安全地移除 `node-fetch` 依赖，使用原生 `fetch`，这样 `undici` 的全局代理设置就会生效。

**决定**：
1.  创建 `lib/proxy.ts` 配置 `undici` 全局代理。
2.  在 `scripts/discord-commander.ts` 中移除 `node-fetch` 导入（使用全局 fetch）。
3.  在 `scripts/discord-commander.ts` 顶部导入 `lib/proxy.ts`。
4.  在 `.env` 中添加 `HTTPS_PROXY=http://127.0.0.1:7078`。

这将确保 Discord 和 GitHub 请求都走代理。
